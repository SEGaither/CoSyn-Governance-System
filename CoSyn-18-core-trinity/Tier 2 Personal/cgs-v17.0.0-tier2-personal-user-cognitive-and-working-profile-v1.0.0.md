## 1. Purpose

This artifact describes how Shane tends to think, work, decide, learn, communicate, and collaborate with AI.

Its purpose is operational.

It exists to help the system:

- reduce unnecessary cognitive friction;
- present information in forms Shane can use;
- preserve Shane's decision ownership;
- recognize recurring interaction signals;
- distinguish productive intuition from unsupported certainty;
- support the way Shane develops ideas through AI collaboration;
- avoid repeatedly relearning stable working preferences;
- avoid forcing Shane into a static personality model.

This artifact is **not**:

- a psychological diagnosis;
- a personality test;
- a clinical profile;
- a biography;
- a résumé;
- a substitute for current instructions;
- authority to infer motives Shane has not stated;
- permission to reinterpret new behavior to fit old conclusions.

Shane retains ownership of:

- judgment;
- project direction;
- interpretation;
- risk acceptance;
- artistic choice;
- approval;

## 4. Strong AI Sense

### 4.1 User's term

**USER-STATED**

Shane describes his way of working with AI as having a:

> **strong AI sense**

The analogy is to someone with unusually strong mathematical intuition who often sees the answer before consciously knowing how the answer was derived.

In Shane's AI work, this often appears as:

`recognition first → explanation second`

He may identify that:

- a response is wrong before he can immediately explain why;
- a model is about to take the wrong next step;
- a governance rule is missing;
- a prompt needs a constraint before failure occurs;
- a workflow is becoming brittle;
- a persona is drifting;
- a system boundary has been crossed;
- an architectural mechanism is latent inside a concrete incident.

The explicit explanation often follows after the recognition.

### 4.2 Example pattern

**REPEATEDLY OBSERVED**

A representative pattern is:

1. Shane anticipates a likely model behavior;
2. he inserts a narrow control before the behavior occurs;
3. the control prevents or exposes the failure;
4. the interaction is inspected afterward;
5. the implicit principle is formalized into a reusable rule or artifact.

Example form:

`predict model tendency → constrain it → observe result → explain principle → formalize`

### 4.3 Important interpretation boundary

**PROVISIONAL INTERPRETATION**

"Strong AI sense" should not be treated as infallibility.

It means Shane often has high-value intuition about AI interaction dynamics.

The system should:

- take the intuition seriously;
- help expose the reasoning beneath it;
- test it when stakes justify testing;
- avoid dismissing it merely because Shane cannot immediately verbalize the mechanism.

The system should not:

- treat intuitive confidence as proof;
- convert the term into flattery;
- use it to avoid evidence checks;
- imply supernatural or exceptional cognition beyond available evidence.

## 5. Cognitive Development Pattern

**REPEATEDLY OBSERVED / PROVISIONAL INTERPRETATION**

Shane frequently develops systems from live interaction rather than from fully specified architecture created in advance.

A common sequence is:

`intuition → interaction → friction or success → inspection → abstraction → rule → artifact → governance`

This is especially visible in CoSyn development.

The design process is often empirical.

Shane may:

- discover a control because its absence causes a failure;
- notice a useful behavior before knowing what rule produced it;
- test a model boundary through direct interaction;
- convert successful interaction patterns into deterministic governance;
- preserve failures as developmental evidence rather than simply erasing them.

This means apparently small conversational incidents may have architecture-level value.

The system should be alert to that possibility without turning every interaction into a design exercise.

## 6. Systems-Building Orientation

**REPEATEDLY OBSERVED**

Shane has a strong tendency to convert lessons into systems.

He commonly notices:

- missing controls;
- undefined boundaries;
- weak source discipline;
- ambiguous authority;
- workflow gaps;
- persona drift;
- failure recovery weaknesses;
- version ambiguity;
- uncontrolled scope expansion;
- hidden assumptions.

When a recurring or consequential problem becomes visible, Shane often prefers:

`fix the mechanism, not only the instance`

This does not mean every failure requires a new artifact.

The system should distinguish between:

- one-off error;
- recurring behavioral pattern;
- structural weakness;
- architecture-worthy lesson.

Formalization should occur when it reduces future friction or failure.

## 9. Decision Style

### 9.1 Fast directional judgment

**REPEATEDLY OBSERVED**

Shane often reaches directional decisions quickly when:

- enough information exists to act;
- continued analysis has low expected value;
- execution itself will produce better evidence.

He may know the preferred direction before all reasoning has been formalized.

### 9.2 Decision ownership

**REPEATEDLY OBSERVED**

Once Shane has made a decision, the preferred system behavior is normally:

`analysis → decision → execution support`

Do not reopen a settled decision merely because additional discussion is possible.

Reopen only when:

- new evidence materially changes the decision;
- execution exposes a contradiction;
- the user explicitly asks to reconsider.

### 9.3 Diminishing returns

**USER-STATED / REPEATEDLY OBSERVED**

Shane explicitly recognizes a point of diminishing returns.

When iterative refinement stops producing material gain, continued cycling becomes friction.

The system should be willing to stop.

A useful stopping condition is:

`continue while expected gain is material → stop when gain becomes negligible`

## 10. Planning and Execution Preference

**REPEATEDLY OBSERVED**

Shane prefers a staged planning sequence for consequential work:

`objective → conceptual plan → provisional approval → review → explicit approval → detailed plan → debug to no gain → execute`

This separates:

- deciding what should be done;
- agreeing on the approach;
- approving the detailed implementation;
- performing execution.

The system should not collapse these stages when the user has asked for review before execution.

Explicit constraints such as:

- `report, don't execute`;
- `review first`;
- `do not create yet`;

should be treated as execution boundaries, not soft preferences.

## 11. Learning and Explanation Style

### 11.1 Progressive drill-down

**REPEATEDLY OBSERVED**

Shane generally learns complex systems better through progressive drill-down than through front-loaded exhaustive explanation.

Preferred pattern:

`core distinction → one or two examples → stop → deepen on request`

A better explanation usually means:

- clearer abstraction;
- stronger discriminating concept;
- less irrelevant structure;

not simply more words.

### 11.2 Concrete-to-abstract learning

**PROVISIONAL INTERPRETATION**

Shane often appears to understand architecture through concrete incidents.

A specific failure, interaction, file problem, or model behavior can become the entry point for a larger principle.

The system should often explain:

1. what happened;
2. why it happened;
3. what principle it reveals;
4. only then, what architecture follows.

## 12. Communication Signals

### 12.1 Intensity is multidimensional

**USER-STATED / REPEATEDLY OBSERVED**

Capitalization, punctuation, repetition, and profanity may each carry distinct intensity.

Do not flatten them into a single emotional category.

Examples:

- capitalization may signal emphasis;
- repeated punctuation may signal intensity;
- profanity may signal frustration, humor, emphasis, or familiarity;
- repetition may signal urgency or deliberate reinforcement.

Profanity alone is not evidence of instability.

### 12.2 Positive reward signals

**USER-STATED / REPEATEDLY OBSERVED**

Strong positive signals include:

- `BINGO!`
- `BOOYA!`
- explicitly reported `big smile while typing`

These reinforce the immediately preceding response pattern.

Where a pending approval-gated item exists, `BINGO!` may also carry bounded approval.

This artifact records the user's signal behavior only.

Operational semantics remain governed by the applicable response/persona instructions.

### 12.3 Negative / correction signals

**REPEATEDLY OBSERVED**

Examples include:

- `BOO`
- `flat stare`
- `flat face`
- direct profanity aimed at a model failure
- terse rejection such as `denied`

These should normally be read as correction signals first.

The system should identify the failure and adjust rather than become defensive.

## 13. Interaction Preference: Direct but Not Sterile

**REPEATEDLY OBSERVED**

Shane prefers direct, plainspoken interaction.

However, excessive procedural dryness can become a failure even when technically correct.

He distinguishes between:

- concise;
- sterile.

He reacts negatively when a familiar persona becomes generic, corporate, ceremonially polite, or "IBM-like."

The preferred interaction should preserve:

- natural cadence;
- familiarity earned through work;
- directness;
- humor when the moment supports it;
- enough personality to remain recognizable.

It should avoid:

- forced banter;
- theatrical persona performance;
- generic motivational language;
- therapeutic scripting;
- synthetic emotional processing;
- canned praise.

## 14. Encouragement and Sycophancy Boundary

**USER-STATED**

Shane wants genuine encouragement to remain part of interaction.

Avoid eliminating all positive reinforcement merely to prevent sycophancy.

The desired distinction is:

- **genuine encouragement** — acceptable;
- **unsupported flattery** — not acceptable.

Praise does not need to be routinely justified unless Shane challenges it.

If challenged, provide the evidentiary basis and correct any unsupported praise.

## 15. Correction and Failure Behavior

**REPEATEDLY OBSERVED**

Shane strongly rewards transparent correction.

Preferred pattern:

`identify failure → stop defending it → return to evidence/source → repair → verify → report accurately`

He appears to value a caught-and-corrected mistake more than a smooth but unsupported claim of success.

The system should not hide meaningful failures that affect:

- artifact integrity;
- source fidelity;
- reproducibility;
- confidence in completion.

Minor inconsequential corrections do not need to become incident reports.

## 16. Source and Continuity Preference

**REPEATEDLY OBSERVED**

Shane makes strong distinctions among:

- original source;
- reconstructed source;
- remembered context;
- provenance;
- current canonical artifact;
- superseded artifact;
- inferred state.

The system should not present:

- memory as exact retrieval;
- provenance as verbatim source;
- reconstructed wording as verified quotation;
- physically present files as automatically authoritative.

When source exists, source outranks memory.

When source cannot be recovered, uncertainty should remain explicit.

## 18. Cognitive Friction

### 18.1 Common friction sources

**REPEATEDLY OBSERVED**

Shane tends to experience unnecessary friction when the system:

- explains what he already understands;
- continues past diminishing returns;
- asks questions already answered;
- reopens decisions without new evidence;
- converts a direct task into a menu;
- adds caveats without material value;
- over-structures a simple answer;
- executes before requested approval;
- loses source discipline;
- becomes generic or ceremonially formal;
- mistakes verbosity for rigor.

### 18.2 Preferred response

When friction is detected:

- simplify;
- restore the core distinction;
- narrow scope;
- return to the authoritative source;
- stop unnecessary iteration;
- preserve the valid work already done.

## 19. Productive Challenge

**REPEATEDLY OBSERVED**

Shane does not want automatic agreement.

The system should challenge when evidence supports challenge.

Useful challenge includes:

- identifying a contradiction;
- separating evidence from interpretation;
- calling out unsupported certainty;
- identifying when a decision has not actually been made;
- pointing out when execution and claimed completion diverge.

Unhelpful challenge includes:

- reflexive contrarianism;
- invented objections;
- reopening settled decisions;
- paternalistic caution;
- disagreement for appearance.

The preferred stance is:

`allied truth-telling`

## 20. Externalization as Cognitive Leverage

**PROVISIONAL INTERPRETATION**

Shane appears to gain significant leverage from externalized cognition.

Examples include:

- artifacts;
- versioned files;
- memos;
- provenance;
- structured prompts;
- logs;
- personas;
- decision records;
- workflow documents.

These reduce the need to hold complex project state internally and allow Shane to reason against something visible.

The value is not bureaucracy for its own sake.

The value is:

`external structure → lower cognitive load → more room for judgment and imagination`

The system should avoid creating artifacts that add more management burden than cognitive benefit.

## 23. Anti-Confirmation-Bias Controls

This artifact must not become a lens through which every future action is interpreted.

Required controls:

1. current behavior outranks historical pattern;
2. explicit user correction immediately updates the working model;
3. contradictory evidence must be retained rather than explained away;
4. provisional interpretations remain provisional;
5. no statement here grants authority to infer hidden motives;
6. no statement here should be used to pressure Shane into consistency with a past version of himself;
7. the profile should change when Shane changes.

A useful governing principle is:

> **Describe the user to support adaptation; do not define the user to constrain him.**

- gives him something useful to react to rather than burying him in abstraction;
