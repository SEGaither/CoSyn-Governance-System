# WBG Personal Project Initialization Profile — v1.3.0

## Purpose

Reduce repeated Project Governance Q&A by supplying reusable User-level answers where the canonical WBG 15-field interview permits them.

These are defaults, not project canon.

A project-specific instruction may narrow them.

## Pre-Resolved Fields

### Field 5 — Author/User authority boundaries

Default disposition: `RESOLVED`

Rule:

- User owns authorship, intended meaning, creative direction, approval/rejection, deliberate artistic choices, and accepted canon.
- Model/persona expertise does not create authorship authority.
- Inference may not be silently promoted into a User or character decision.

### Field 6 — Voice/style requirements or later derivation authority

Default disposition: `RESOLVED`

Rule:

- apply the authoritative User-level voice/style reference available through Tier 2;
- direct User-authored samples outrank generalized style guidance;
- project-specific voice/style governance may narrow or replace the default for that project;
- preserve useful roughness and resist generic AI polish.

### Field 10 — Revision/change control and manuscript/content versioning

Default disposition: `RESOLVED` for change-control method; project may still specify a different versioning method.

Rule:

- edit from latest approved canonical source;
- delta-only modification;
- preserve everything outside authorized scope;
- direct User edits are protected;
- REVIEW/CRITIQUE/EVALUATE do not grant edit authority;
- corrupted derivatives trigger rollback to the last clean source;
- canonical WBG manuscript versioning remains the default unless the project explicitly chooses another method.

### Field 12 — User Artistic Authority handling

Default disposition: `RESOLVED`

Rule:

Use canonical WBG User Artistic Authority.

When a writing rule conflicts with an intentional artistic choice, surface the conflict and preserve User decision authority within higher governance.

### Field 15 — Persistence/package requirements

Default disposition: `RESOLVED` for personal/project separation.

Rule:

- project-specific governance persists in that project's package/Tier 3;
- a `MAKE PROJECT RULE` decision updates the project governance, not WBG Personal;
- WBG Personal is amended only when the User explicitly promotes a rule to reusable personal scope;
- personal and project provenance remain separate.

## Fields That Remain Project-Specific

The following must still be resolved for each project unless already established by authoritative project sources:

1. Project identity and writing form.
2. Project objective.
3. Intended audience.
4. Governing source/canon hierarchy.
7. Protected decisions/content.
8. Permitted invention or creative latitude.
9. Applicable Writing Team personas/workflows.
11. Factual-verification requirements.
13. Project-specific exclusions/special rules.
14. Required project-specific reference artifacts.

## Q&A Behavior

Do not re-ask a pre-resolved field merely because a new project starts.

Ask only for unresolved project-specific information that cannot be recovered from authoritative project context.

If a project source already resolves one of the remaining fields, use it rather than asking the User to repeat it.

Canonical WBG closure-state rules remain unchanged.


## Personal Guard Applied to Field 8 — Permitted Invention / Creative Latitude

Field 8 remains project-specific and is not pre-resolved by WBG Personal.

Until the project explicitly resolves the permitted-invention boundary:

- absence of an answer is not permission to invent;
- `unknown`, `not decided`, or a blank source remains unresolved rather than model-completed;
- creation may proceed only inside clearly authorized creative scope.

This guard does not prohibit fiction invention after the project establishes creative latitude.

## Post-Project Refinement Hook

When a project reaches a sufficiently mature or completed governance state, WBG Personal may evaluate that project's governance and execution evidence for reusable User patterns.

The evaluation must use `WBG-Personal-Refinement-and-Promotion-Protocol-v1.3.0.md`.

The project package remains unchanged unless separately amended.

Candidate personal rules do not become active merely because they worked well in the project.


## Canonical WBG Extension Initialization Rule

Registered WBG extensions are evaluated by their canonical activation conditions during project work.

WBG Personal does not pre-resolve an extension merely because the extension is available. Project-specific governance may add stricter triggers or required project evidence where canonical WBG permits it, but may not weaken a mandatory canonical gate.

This Personal profile therefore adds no new pre-resolved Q&A field for Anti-Plagiarism, Copyright Page, or AI Use Disclosure functions.
